# Screamer Rally: optional improvements

Reviewed 24 November 2026 against Rick-Barber/ScreamerRally-Recomp commit `02d5deb8fe88ba0899bbc7f5a0ad6182fb859035` and the bundled native DOSBox Staging 0.83.1 runtime. Updated after implementation: optional 16:9 camera widening and extended object/scenery admission are now available in the app launch options. The other entries remain a feasibility review.

The baseline wrapper runs `C:\SR\START65H.EXE`, the original software renderer. Rick's executable profiles support only two exact versions of **`STRT3FX.EXE`**, the 3dfx Glide build ([profile/mod.rs:17](https://github.com/Rick-Barber/ScreamerRally-Recomp/blob/02d5deb8fe88ba0899bbc7f5a0ad6182fb859035/crates/sr-runtime/src/profile/mod.rs#L17)). Its reverse-engineering notes are valuable, but its addresses and hooks cannot be applied directly to `START65H.EXE`.

Effort bands below are engineering judgment for one experienced developer, including basic game testing. They are additional to the working wrapper and assume access to the exact executable being modified; remapping the software build adds uncertainty.

| Improvement | Feasibility in this native wrapper | Approximate additional work |
| --- | --- | --- |
| Sharp pixels / CRT appearance, 4:3 aspect correction, fullscreen, VSync | Existing DOSBox settings work with the software and 3dfx builds. Add a small native preferences UI or launch presets. These change the finished picture; they do not add 3D detail. Rick's exact 108-preset ShaderGlass catalogue is a separate shader-porting task: its pack stores precompiled DXBC ([pack.rs:1](https://github.com/Rick-Barber/ScreamerRally-Recomp/blob/02d5deb8fe88ba0899bbc7f5a0ad6182fb859035/crates/sr-crt/src/pack.rs#L1)). | Hours for presets; 1–3 days for polished controls and testing. |
| Controller buttons, analog steering, deadzones | DOSBox already emulates analog joysticks and maps modern pads. Configure the game's bindings/calibration and test the actual controller. Rick's pedal curves and menu behavior would need additional integration. | 1–3 days for a good tested preset; several more for custom controls. |
| Optional original 3dfx graphics | The existing ARM64 DOSBox runtime emulates Voodoo. Use `STRT3FX.EXE` and the matching DOS Glide driver, preserving software mode as another choice. Bilinear filtering becomes a Voodoo setting. CPU cost needs a full-race test; this does not supply Rick's high-resolution renderer. | 1–3 days to configure and validate; allow more if game/driver bugs surface. |
| Unlock tracks/championships/bonus car | Feasible guest-memory or guest-code patch. Rick's implementation also preserves genuine save progression, which requires intercepting load/save and championship events—not merely setting six fields. | A few days for a simple opt-in implementation on a recognized build; roughly a week for comparable reversible save behavior. |
| Autopilot | Rick clears the player's control-binding pointer so the original AI drives, then restores it. A small memory integration is plausible once the executable base and player state are reliably identified. | 2–5 days for one recognized build and race/menu transitions. |
| Choose day/night/fog before a race | Guest patching is feasible. The setting must be applied before asset loading, and absent assets must be checked. The source explicitly excludes night on Stadium. | Several days to roughly 2 weeks, depending on software-build mapping. |
| Switch weather live during a race | Substantially more work: Rick preloads alternative sky/reflection/car assets, invokes guest loaders, swaps model pointers, and rebuilds fog/camera state. | Several weeks, with track/car regression testing. |
| Highest detail / longer draw distance | Requires executable-specific changes to level selection, far clipping, culling math, object-list capacity, and visibility lists. The world is a stage set; simply showing everything exposes missing ground and floating scenery. Rick's detail patch also relies on depth buffering to resolve overlapping representations. | Roughly 1–3 weeks for a conservative prototype; full visual parity is larger. |
| True 16:9 / ultrawide | Requires changing game projection/clipping AND the output viewport/render target and HUD handling. Stretching a 640-wide framebuffer through DOSBox is not equivalent. Rick's backend deliberately displays extra coordinates outside the original 4:3 range. | Several weeks after choosing a rendering strategy; additional uncertainty for software mode. |
| Event-based controller vibration | Controller rumble output is straightforward; reproducing Rick's impacts, landing, surface and wheel-spin feedback requires reading physics state at each simulation step. | Roughly 1–2 weeks after a reliable guest-memory integration exists. |
| Higher-resolution 3D, precise geometry, depth fixes, camera collision | These are custom rendering features. Rick extracts neutral world/scene data and draws it with D3D11; camera collision queries the extracted world. A Mac version needs a Metal/wgpu renderer or substantial DOSBox integration. Enlarging the emulator's framebuffer does not recreate these improvements. | Several months as a coordinated graphics/runtime project. |
| Smooth 60/120/144 Hz interpolated motion | Requires preserving the simulation cadence while drawing extra interpolated camera/object states, including mirror/HUD and rollback of render side effects. Rick uses Windows write-watch memory APIs. Increasing DOSBox CPU cycles or display refresh alone cannot reproduce it safely. | A substantial separate project, likely months alongside renderer/runtime work. |

A closer-term route exists for the current software build. The separate [rea-screamer-trilogy patch set](https://github.com/akitaonrails/rea-screamer-trilogy/blob/master/crates/screamer-launcher/src/fixes.rs#L741) already profiles this exact `START65H.EXE` and implements optional 16:9 camera changes plus a conservative object-admission-distance increase. Porting those checked patches and adding reversible launch presets is likely a days-to-a-couple-of-weeks task. Its 16:9 version stretches the 2D HUD, and its distance change is less comprehensive than Rick's visibility/LOD pipeline. This is a useful subset rather than parity with Rick's implementation. The launch options now include these two checked, reversible software-build patches. The 16:9 presentation shader keeps the picture at 16:9 across different screen and window sizes.

The optional 16:9 and extended-distance settings are implemented. Useful next steps are native controller settings and a tested optional 3dfx mode. Rick-style HUD-aware arbitrary-aspect widescreen, the new renderer, and geometry interpolation remain separate, larger projects.

Before enabling the 3dfx option, port and validate the existing [texture-cache boundary fix](https://github.com/akitaonrails/rea-screamer-trilogy/blob/master/crates/screamer-launcher/src/fixes.rs) for `STRT3FX.EXE`. The game can reach its title screen and still fail later during track previews or texture-cache reuse. This fix is unrelated to the software-rendered baseline and has not been applied here.

There is a useful prototyping route: DOSBox Staging 0.83.1 exposes an optional localhost [memory/register HTTP API](https://www.dosbox-staging.org/0.83/manual/http-api/), including atomic compare-and-swap writes and guest allocation. The actual staged runtime contains these endpoints. This may support small patches without an emulator fork. It does not provide Rick's frame-synchronized callbacks or guest rendering bridge, and upstream says it was primarily tested with the normal CPU core. **The API was not enabled in the user app.**
